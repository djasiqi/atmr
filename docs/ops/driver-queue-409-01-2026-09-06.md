# DRIVER-QUEUE-409-01 — séquence reset au cold start

```text
P0 GPS LIFECYCLE/FGS = PASS / CLOSED
DRIVER-RUNTIME-01    = PASS sur ce périmètre
DRIVER-COLD-01       = FAIL / VISUAL PENDING
DRIVER-QUEUE-409-01  = QUALIFIÉ / BLOQUEUR POTENTIEL
DEPLOY               = BLOQUÉ
CODE MODIFIÉ         = NON
```

Indépendant du P0 FGS. Ne pas vider l’app, le ledger, la DLE, Redis, Kafka ou PostgreSQL pour faire disparaître le 409.

## Contrat exact du code

Session **réutilisée** si le blob `driver_tracking_session_v1` est encore dans le TTL :

```text
trackingSessionId + sessionGeneration restaurés
sequenceCounter   = max(sequence_id) des items ENCORE dans la file
                  = 0 si pending_count = 0
```

Le blob persisté **ne contient pas** `sequenceCounter` :

```ts
// persistSession()
{ trackingSessionId, createdAt, sessionGeneration }
```

`POST /driver/me/tracking/sessions` renvoie `first_sequence_id` et le client sait s’en servir (`sequenceCounter = max(counter, first_sequence_id - 1)`), **mais seulement** dans `registerSessionWithBackend`.  
`load_persisted` avec `sessionGeneration` déjà présent passe READY **sans** re-register → le seed serveur n’est jamais lu.

`reconnect_resync` (`rotated: false`, `session_unchanged: true`) ne restaure pas non plus le watermark.

Le watermark HTTP (`contiguous_persisted_through`) ne sert qu’à tombstoner les `ingested_non_persisted`, pas à recaler le compteur d’une file vide.

**Verdict contrat :** ce n’est pas une rotation manquante. C’est une **restauration du compteur absente** alors que la session est volontairement réutilisée. `first_sequence_id` existe déjà pour ça ; le trou est `load_persisted` qui court-circuite le register.

409 `session_sequence_already_persisted` = même `(session, sequence)`, autre `event_id`. SQLite conservée. Le flush traite le 409 comme une erreur HTTP générique (retry jusqu’à `MAX_RETRIES` puis drop), pas comme un signal de recaler le compteur.

## Preuve smoke 20:29 (fenêtre 60 s complète)

L’extrait coupé vers 18:29:12 UTC ne montrait que la collision. La fenêtre entière (`P0-GATE-APP.txt`) :

```text
20:29:34.845  load_persisted
              session = trk_sess_1788717983684_2d4rugcl
              generation = 24
              pending_count = 0   → sequenceCounter = 0

20:29:36.408  reconnect_resync
              rotated = false
              session_unchanged = true

puis           sequence_id 1, 2, …  → 409 (5 HTTP 409 dans le PID)
20:29:36.674  head seq collision    retry_count=5  queue_depth=2  acked=0
20:29:38.543  1er backend_acked=1   (seq 4/5, points NEUFS)
20:29:38.545  queue_depth=2         head collision toujours en retry (count=7)
20:29:59.131  queue_depth=0         acked=1  seq 6
20:30:04–21   seq 7, 8, 9           acked=1  depth=0  plus de 409
```

Les acceptations tardives ne prouvent **pas** la continuité : le compteur a simplement dépassé le `max_seen` serveur pendant que les seq 1–2 retryaient. Au prochain cold start file vide, seq reprendra à 1 et le 409 reviendra.

## Décision (pas encore implémentée)

Deux voies compatibles avec le contrat existant — **ne pas trancher ici** :

1. **Restaurer le compteur** (aligné sur `first_sequence_id` / watermark) : persist `sequenceCounter` **et/ou** re-register / watermark au `load_persisted` même si generation est déjà READY.
2. **Rotation explicite** au cold start si file vide : nouveau `tracking_session_id`, register, `first_sequence_id=1`.

Ne pas masquer le 409 par une purge stockage / PG / Redis.

## Gate avant deploy (après le choix)

```text
aucun 409              sur les séquences suivantes
séquence monotone      après cold start
  OU rotation          explicite et valide
```
